## 2. Data design

**Four new file kinds, each one file per thing.** None changes an existing file kind's meaning.

| Folder | Schema (new) | What it defines | Changed only by |
|---|---|---|---|
| `processes/<id>.json` | `process.json` | the event log, its clean-up, the reference model, the SLAs | `save_process`, `delete_process` (confirmed) |
| `apps/<id>.json` | `app.json` | one whole app: screens, navigation, blocks, forms | `save_app`, `delete_app` (confirmed) |
| `graphs/<id>.json` | `graph.json` | which objects and links form a graph and what is computed on it | `save_graph`, `delete_graph` (confirmed) |
| (in `processes/<id>.json`) | | the reference model is a part of the process file, not a file of its own | |

Each gets one `LAYOUT` line (`imports.py:30`), one `references` function called from `_references` (218), one lineage builder in `BUILDERS` (245) and kinds in `LineageInput` (277). `bundle.bundle` needs no change.

**What points where, without copying**

| Field | Points to | Never copies |
|---|---|---|
| `processes[].events[].objects[].type` | an object type in `model/ontology.json` | the key, the title |
| `processes[].events[].table`, column names | a model table and its columns | types (read from the lake) |
| `apps[].screens[].blocks[].action` | an action type in the ontology | its inputs (the form is built from them) |
| `apps[].…blocks[].visual` | `reports/<id>.json` page and visual | the query |
| `apps[].…blocks[].process` | `processes/<id>.json` | |
| `graphs[].links` | link IDs in the ontology | the join path |

**Git or lake**

| In Git (definitions) | In the lake (derived or written data) | In Postgres |
|---|---|---|
| `processes/*.json`, `apps/*.json`, `graphs/*.json` | `pm_<id>_events`: one row per event | `analysis_runs`: one row per process build and graph run (status, times, rows, dropped rows by reason, error) |
| generated KPI measures in `model/measures.json` (written on approval) | `pm_<id>_<type>`: the events of each object of that type, in order (the flattened log) | |
| generated tables, keys and relationships in `model/model.json` (as `ml._predictions` does) | `pm_<id>_<type>_cases`: one row per case, one-to-one with the object | |
| properties on object types in `model/ontology.json` (as `ml._on_object` does) | `graph_<id>_<type>`: one row per object with its scores, one-to-one with the object | |
| an approved link's definition in `model/ontology.json` | `graph_<id>_pairs`: proposed pairs (similar, predicted) with evidence | |
| | `links_<id>`: an input table of approved predicted links (written through `writeback._batch`) | |

A BPMN file is read once and turned into the JSON reference model; the file itself is not kept. An OCEL 2.0 file is a source like any upload; an OCEL export is a download, not a project file.

**Schema numbers.** `db.SCHEMA_NUMBER` 7 → 8 (one new table, `analysis_runs`, shaped like `optimizer_runs`). Three new JSON schemas. `project.json` gains the optional `published_from` (M6). `report.json`, `flow.json`, `ontology.json`, `measures.json`: unchanged.

**Reserved names.** `pm_`, `graph_` and `links_` are prefixes of generated tables. A build refuses with the clashing table's name if a person's table already has one; nothing is reserved in a project that has no process or graph file.

### 2.1 The process file

```json
{
  "$schema": "https://schema.abi.invalid/v1/process.json",
  "id": "supply", "name": "Supply", "description": "From a café's purchase order to the paid invoice.",
  "case": "purchase_order",
  "events": [
    {"table": "supply_events", "id": "event_id", "activity": "activity", "start": "started_at", "end": "ended_at",
     "attributes": ["done_by", "amount"],
     "objects": [{"type": "delivery", "columns": ["delivery_id"]},
                 {"type": "purchase_order", "through": "supply_event_orders", "event": "event_id", "columns": ["po_id"]}]},
    {"table": "purchase_orders", "stamps": {"Order placed": "placed_at", "Order approved": "approved_at"},
     "objects": [{"type": "purchase_order", "columns": ["po_id"]}]}
  ],
  "clean": {"rename": {"GR": "Goods received"}, "drop": ["Heartbeat"],
            "where": [{"column": "started_at", "op": ">=", "value": "2025-01-01"}], "duplicates": "drop"},
  "reference": {"from": "variant", "start": ["Order placed"], "end": ["Invoice paid"],
                "flows": [["Order placed", "Order approved"], ["Order approved", "Goods received"],
                          ["Goods received", "Invoice received"], ["Invoice received", "Invoice paid"]],
                "optional": ["Reminder sent"], "any_order": [["Goods received", "Invoice received"]],
                "repeat": {"Goods received": 2}},
  "sla": [{"id": "delivered_in_5_days", "name": "Delivered within 5 days", "from": "Order approved",
           "to": "Goods received", "within_hours": 120}],
  "refresh_minutes": 60
}
```

- `events` lists one or more sources. A source is either an event table (`activity` + `start`, optional `end`) or a table with several timestamp columns (`stamps`: activity name → column), which is unpivoted.
- `objects` says which objects an event is about. `columns` is a foreign key on the event row (at most one object of that type). `through` names a bridge table (several objects of that type per event). This is the object-centric part.
- `case` is the object type a view starts from. Any type listed under `objects` can be chosen in the view.
- `clean`: rename, drop, a filter (the semantic filter shape), and what to do with identical events. Rows with no timestamp or no object are always dropped. Every dropped row is counted by reason in the build's run; nothing is dropped silently.
- `reference` is the allowed behaviour: start and end activities, allowed directly-follows pairs (`flows`), optional steps, sets that may come in any order (a BPMN parallel gateway), and how often a step may repeat. `from` records where it came from: `variant`, `drawn`, `bpmn` or `discovered`.
- Derived, never stored in the file: variants, the directly-follows graph, durations, the happy path (the reference's own path, or the most frequent conforming variant).

**The lake tables a build writes** (by DuckDB SQL, one snapshot):

| Table | Rows | Key and relationships | Read by |
|---|---|---|---|
| `pm_supply_events` | one per event: id, activity, start, end, attributes | key `event_id` | object-centric totals; denied to restricted Viewers when a type's table is filtered |
| `pm_supply_purchase_order` | one per (event, purchase order): the event's columns plus `seq`, `next_activity`, `wait_seconds` | many-to-one to `purchase_orders` and to `pm_supply_events` | map, variants, timeline; filtered by the object's row rules (forward, as today) |
| `pm_supply_purchase_order_cases` | one per purchase order: `started`, `ended`, `open`, `cycle_hours`, `events`, `variant`, `rework`, `happy`, `conforms`, `deviations`, one flag per SLA, `last_activity`, `waiting_hours` | key = the object's key, one-to-one | KPIs as measures, properties on the object, alerts per case |

**No double counting** (item 11 of the scope):
- an event's own figures (how many events, a cost or amount attribute, working time) are counted from `pm_<id>_events`, once per event;
- a view of one object type counts per object of that type, and says so ("per purchase order");
- frequencies of two types are never added. A measure over `pm_<id>_<type>` that sums an event attribute is refused at save with the fix ("use the events table").

### 2.2 The app file

```json
{
  "$schema": "https://schema.abi.invalid/v1/app.json",
  "id": "cafe-visits", "name": "Café visits", "icon": "check", "start": "list",
  "nav": [{"screen": "list", "label": "Cafés"}, {"screen": "supply", "label": "Supply"}],
  "screens": [
    {"id": "list", "name": "Cafés", "blocks": [
      {"id": "kpi", "type": "visual", "visual": {"report": "cafe-visits", "page": "main", "visual": "by-cafe"},
       "layout": {"x": 0, "y": 0, "w": 12, "h": 4}},
      {"id": "cafes", "type": "objects", "object": "cafe", "columns": ["city", "seats", "cafe_contacts.manager"],
       "select": "cafe", "then": {"screen": "detail"}, "layout": {"x": 0, "y": 4, "w": 12, "h": 8}}]},
    {"id": "detail", "name": "Café", "needs": ["cafe"], "blocks": [
      {"id": "card", "type": "object", "object": "cafe", "layout": {"x": 0, "y": 0, "w": 7, "h": 8}},
      {"id": "flag", "type": "form", "action": "flag_visit", "on": "cafe",
       "fields": [{"input": "reason"},
                  {"input": "follow_up_on", "label": "Follow up on",
                   "show_when": {"value": "{{ inputs.reason }}", "op": "!=", "to": ""}}],
       "then": {"screen": "list"}, "layout": {"x": 7, "y": 0, "w": 5, "h": 8}, "phone": {"order": 1}}]},
    {"id": "supply", "name": "Supply", "blocks": [
      {"id": "map", "type": "process", "process": "supply", "view": "map", "layout": {"x": 0, "y": 0, "w": 12, "h": 10}}]}
  ]
}
```

- Block types: `visual` (a report's visual, or an inline `query`), `objects` (a list of one type), `object` (one object's card), `form` (an action type), `process` (map, variants, a KPI or a case timeline), `text`, `button` (go to a screen), `filter`.
- **Free layout**: `layout` is x, y, w, h on a 12-column grid, as report visuals use. `phone` gives the order or hides a block; by default a phone shows blocks in reading order, one column.
- **Navigation**: `nav` is the menu; `then` moves to a screen after a click or a submit; `select` puts the chosen object into the app's selection, and a screen with `needs` opens only with one.
- **Forms**: the fields come from the action type's `inputs`. `fields` only orders, labels and hides them. `show_when` is the `when` shape (`flows._holds`). A required input may be conditional only if it has a default. The engine validates every submit against the action's own `inputs`, whatever the app shows.
- An app file holds no HTML, no script, no expression language, no colour and no address outside the app. Text is plain text.

### 2.3 The graph file

```json
{
  "$schema": "https://schema.abi.invalid/v1/graph.json",
  "id": "visits", "name": "Who visits where",
  "objects": ["customer", "cafe"], "links": ["visited"], "weight": "count",
  "compute": [
    {"kind": "centrality", "method": "pagerank", "on": "cafe", "property": "importance"},
    {"kind": "communities", "on": "customer", "property": "group"},
    {"kind": "similar", "on": "customer", "top": 10},
    {"kind": "predict_links", "link": "visited", "top": 5}
  ],
  "audience": "unrestricted", "time_limit_s": 300
}
```

- The graph is read from the lake through the ontology's links, held in memory for the run, and dropped. No graph database.
- `compute` kinds: `centrality` (degree, pagerank, closeness, betweenness), `communities`, `similar`, `predict_links`. Shortest path and reachability are questions asked at read time, not stored (`graph_path`, `graph_reach`).
- Scores are written to `graph_<id>_<type>` and become properties of the object type, as a prediction does.
- `audience`: who may see whole-network scores (section 6, point 4). `unrestricted` is the default.

## 5. Security review points

1. **Viewers submitting forms on the published app (M6).**
   - The run happens in the working project as the person: role, visibility of the object under their row rules, the inputs' schema, the checks and the confirmation are the ones of `run_object_action` (941). The copy never writes by itself.
   - Only action types an Owner granted to Viewers (`imports.grants` 599) reach the copy. The first Publish that carries forms is an Owner's confirmation naming them.
   - The published action must equal the working one, or the run is refused: an Editor's unpublished change can't be reached by a Viewer.
   - `writeback.carry` is one way, replays logged batches only, starts no flow and takes no value from the copy.
   - What a Viewer types is data: a flow's agent step gets it capped and never as instructions; it can't redirect mail outside the members (1.2.6 item 28).
   - The agent never submits: in Viewer mode the harness refuses, and through the bridge a write is a proposal.
   - A cap per person per minute; every run is in the audit log and undoable by an Editor.
2. **The public share view (M9).**
   - The pass-through is an allow-list of exact paths and methods; it forwards one header and a capped body, and never a session or the agent's key.
   - The token is in the fragment only. Check the app's log, the engine's log and the Referer of every outgoing request.
   - No link in a project with row rules. A link shows one report as its creator, read-only, until it expires or is revoked; revoking works at once.
   - The page has no forms, no actions, no chat and no way to another page of the app.
   - Rate limits at both servers. Hooks stay HMAC-signed with their 64 KB cap; the embed page keeps its `frame-ancestors`.
   - Agents can't make a link, an embed key or a hook token, however the request arrives.
3. **BPMN and OCEL parsing (M4).**
   - XML: any DOCTYPE or ENTITY is refused before parsing; caps on size, elements and depth; no network, no file access; names are text, never evaluated.
   - OCEL JSON: schema-checked whole, a size cap, loaded through the ordinary upload path into ordinary tables.
   - Names from a file can carry instructions for the agent: they are data, shown quoted, and a file's text is never followed.
   - An OCEL export is a data export as the person: row rules and hidden columns apply, the export area's caps apply, and it holds no secret and no host.
   - Both parsers live in one file and are fuzzed in the container.
4. **Graph scores and row rules (M10).** A whole-network score is worked out from links a restricted person can't see: a degree is a count of hidden rows.
   - Default: `graph_<id>_*` tables are made from every row, so they are denied to restricted Viewers (`rls.unfiltered_outputs`), like a prediction table without an object. Fail closed.
   - An Owner may set `audience: "everyone"` on a graph file, in a confirmation that says in words what a restricted person will then see ("each Customer they can see shows a score worked out from visits they cannot see"). Scores then follow the object's visibility. Pairs never widen: both ends must be visible.
   - Paths, reach and "similar to this" asked at read time run over the person's own visible links, as the person. They can differ between people, and the page says "among what you can see".
   - A run's size and time are capped; the run is a job in the worker, never in a request.
5. **App files as an injection surface for the agent (M7, M8).**
   - An app file holds data only: no markup, script, expression or outside address. The page writes text as text.
   - Labels and help texts reach the agent when it reads or edits an app. They are data: the harness marks them, `test_app_text_is_data_not_instruction` plants an instruction in a label, and the reviewer adds two more.
   - A form in an app can do only what its action type allows; the app can't add an input, loosen a check or change who may run it. Hiding a field is cosmetic; the engine checks the action's own schema.
   - A block shows only what the person's own reads return; `apps` leaves out blocks a person can't use.
   - The app-builder specialist has no write tool but `save_app`, `add_block` and `delete_app`, each a confirmed save.
6. **Process tables (M1-M5).** The flattened tables follow the objects' rules by the existing forward direction; the events table is denied when any of them is filtered; KPIs for a restricted person are over their own cases. Root cause compares only what the person can see.
7. **The follow-link key table (M0).** It holds keys the person may see and nothing else; no SQL a restricted person writes can name it; it is built by a system read inside the person's lock and dropped with its snapshot; two people share one only when their condition text is identical.
8. **The name and the theme (M12).** No external font or style is fetched (`tests/test_fonts.py`); emails keep their headers; the visible name changes no address, cookie or token name.

## 8. How 1.2.7 is built: the engineering loop

As 1.2.6 used it (docs/plans/1.2.6-loop.md), for every milestone:

1. **Maker.** A fresh implementer builds the milestone's items with the tests named for them. It reads this plan and the loop file first. It never grades its own work, edits the contract, weakens a test or pushes.
2. **Machine gate.** `.loop/gate127.sh <M> <base>` on pve1 in a throwaway container: the whole suite, the milestone's named tests from `docs/plans/1.2.7-gates.json`, the golden test byte-identical, the `also` targets that are measurable there. The only failures allowed are the six container-only ones named in RELEASE.md.
3. **Fresh independent reviewers each round.** A new reviewer reads only the plan, the diff and the gate's output, never the maker's report. It checks correctness against the targets, security against section 5, that no test was weakened, and simplicity. M0, M4, M6, M9, M10 and M13 add a security reviewer. Findings are high, medium or low, each with file and line.
4. **Fix.** Every confirmed finding is fixed; then steps 2 and 3 again.
5. **Secret scan and push.** Then GitHub CI must be green.
6. **Report to the owner:** what was built, test counts, findings and fixes, the risks left. Only then does the next milestone start.

**Stop rules.** Done: the gate all PASS, CI green, no high or medium finding left. Budget: at most 4 rounds per milestone; when a fifth would be needed the owner decides. Blocked: the same check failing twice with the same cause stops the loop. Never: tag, merge, publish or touch the live install without the owner's yes; never run anything on the Mac.

**Lessons from 1.2.6, now rules:**
- **Targets go into the contract before the build.** Every `also` in the gates file is a number with its unit and how it is measured. A target found too loose or too tight is changed by the owner, not by the maker.
- **Bench results are recorded when measured,** in bench/RESULTS.md with the commit, the machine and the command, in the same round. A comparison needs both sides measured the same day (1.2.6 had no 1.2.5 number to compare with).
- **The release run checks every address a person is given** (item 74): does it route through the app's own address?
- **The reviewers check the sentences shown to people for truth:** each refusal, confirmation, hint and docs sentence the milestone adds is tried on the server. A sentence that is not true is a medium finding.
- **The owner tries each visible milestone on the server before the next one builds on it.** Each of M3, M6-M12 has its short click-through list above, with what was assumed. The coordinator sets up a throwaway install with Brewline and gives the owner its address; the owner's notes go into the loop file.
- **Sketches before screens** (M3, M7, M8, M11, M12): the owner's OK is recorded in the loop file before the maker starts.

## Coordinator decision in M0 (13 Nov 2026): item 2 is built with a key TYPE, not a key table
