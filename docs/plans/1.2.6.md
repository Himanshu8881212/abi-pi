## 1. Where the code is today

**The semantic model** (`abi/semantic/model.py`)
- `model/model.json` holds the tables (kind, description, hidden), the `entities` (id, table, key), the relationships, `date_table` and `rates_table`. `load` (52) merges entities into the tables. `save` (63-73) rebuilds `entities` from the table keys, so any `name` or `description` on an entity is lost.
- The schema (`engine/schemas/v1/model.json`) already allows `entities[].name` and `.description`, but nothing keeps them. An "entity" today is just a keyed table.
- `build_model` (166-190) stores what `detect` proposes, keeps a person's overrides and adds at most one relationship per table pair (180-187).
- `add_relationship` (225-239) allows many-to-one only, onto the target's key, and turns the target into a dimension. `remove_relationship` (246) is destructive and records a tombstone in `removed_relationships`.
- `check` (308-377) is readiness. `semantic_model` (398-415) is what the agent reads; `_relevant` (418) trims it in big projects.
- The glossary lives in `model/glossary.json`. `set_glossary_term` (458) and `masked` (440) hide agent-written terms from restricted Viewers. Memory notes link to term IDs (`terms`, 490).
- Named models (`models.json`, 495-567) are table and measure subsets. They are the precedent for "one model, several views".
- `abi/semantic/detect.py`: `detect` (64) finds keys, the date table and relationships by name match plus at least 95% overlap (106-125). Every target is one table's key, so it only ever finds fact → dimension links.

**MEL** (`abi/semantic/mel.py`)
- An `Agg` leaf belongs to one fact (`Agg.col.table`). `Where`, `Ignore` and `Time` change the filter context (1-10, 37-100).
- There is no notion of objects or links. MEL needs no change.

**The query compiler** (`abi/semantic/planner.py` and `abi/semantic/__init__.py`)
- `planner.path` (131-149) is the only join logic. It takes a breadth-first walk outward along many-to-one relationships from the fact (`r["from"]["table"] == current`) and returns the shortest chain to the target table.
- So it **can**:
  - follow several many-to-one hops (fact → dimension → dimension, D-06), joined hop by hop with `LEFT JOIN` (`_aggregate` 440-441, 524-525);
  - filter or group by any table reachable that way;
  - measure a dimension table: an `Agg` over `customers` makes customers the fact of that context.
- It **cannot**:
  - (a) walk a relationship against its direction (one → many), so a measure over `customers` can't be grouped by `cafes.region`: "has no relationship" (143);
  - (b) use a many-to-many path through a bridge or fact, such as customer ↔ café through `orders`;
  - (c) choose between two shortest paths. It refuses with "the planner can't choose" (145-148), which is also why `build_model` adds only one date link per table;
  - (d) reach one table by two routes in one query: joins are aliased by table name (`rels` is `{table: rel}`, 440);
  - (e) run time intelligence through a dimension: the date table must link to the fact directly (489-492);
  - (f) fold more than one hop into query copies (`copy_sql` 250-266), or group by key with more than one joined table (`by_key` 456).
- `SemanticQuery` (`__init__.py` 463-473) has no field that names a path. The same query shape is copied in four schemas: `datasets.json` `$defs.query`, and the copies in `report.json`, `flow.json` and `tool.json`, each with `additionalProperties: false`.
- The plan is the cache key (SE-7; `_plan` 557-616 feeds `execute` 321-392). If the SQL text changes, every cache entry and every M3.6 shared partial is new.
- Row-level reads besides the planner: `table_rows` (791, the grid; any role can call it through `get_rows` 884) and `preview_steps` (826). `sql_query` (`semantic/sql.py:232`) is open to Viewers too.

**Security** (`abi/semantic/rls.py`, `abi/security/`)
- Rules live in `security/rls.json`.
- `conditions` (173-251) builds one filter per table:
  - its own rules;
  - plus `fk IN (<visible keys>)` for every many-to-one relationship into a filtered table (step 216-241);
  - repeated to a greatest fixpoint (247-250).
- So RLS follows relationships **one way only**: a fact is filtered by its dimensions, never a dimension by its facts.
- Views are lists of constants, never joins (header, `_in` 103-116).
- A NULL foreign key passes no `list_contains`. If a dimension becomes filtered, rows that don't point at it (anonymous orders) disappear. Any reverse filtering must not cause this.
- `filtered` (270), `key_columns` (260, M3.6 shared partials), `explain` (326) and `_unfiltered_outputs.roots` (311-318) all walk the same one-way direction.
- `check` (447) allows a restricted user's SQL only when it is one SELECT over unqualified known tables and allowed functions. `IN (subquery)` passes.
- `_digest` (67-73) hashes `model/*.json`, so a new file in `model/` invalidates the RLS and plan caches with no extra code.
- Column rules come from `hidden` (76) and are enforced in `_plan` (594-603) and the views' `EXCLUDE` (385).

**Write-back** (`abi/writeback/__init__.py`)
- Edits are addressed by key. `_table` (215) refuses tables with no key. `_batch(user, Edits, status)` (253-329) is one snapshot, logged with old and new values.
- An agent's edits become proposals: `edit_cells` (338) when `by_agent()`, otherwise `propose_edit` (355). `approve_edit` (366) applies them.
- `_fire` (346) starts write-back flows. Input tables come from `create_input_table` (454).
- Edits never check RLS: only Editors write, and Editors are never restricted.

**Flows** (`abi/flows/__init__.py`)

- `resolve` (181) fills `{{ data.x.y }}`; a whole-field template keeps the value's type, such as a list.

- `_data_condition` (586-621) holds one state row per flow (`flow_conditions`, `db.py:265`). `after_refresh` (624) has the D-23 loop guard.
- `_step` (295) runs each step as the flow's owner (FL-6). `_save` (685) confirms enabling and first sends.
- `send_email` and `post_message` (`abi/tools/builtin.py:526, 553`) confirm the first send per domain or channel (`_first_send` 505) and check grounding.

**ML** (`abi/ml/__init__.py`)

- `unfiltered_outputs` blocks an `ml_<id>` for restricted Viewers whenever its upstream is filtered by rules its own relationships don't reach. Today that blocks predictions on `customers` trained on `orders` when the rule is on `cafes`.

## 2. Data design

**One new file: `model/ontology.json`.**
- I keep it out of `model.json`. That way `model.json` stays byte-identical, `save` (63) keeps rewriting it as today, and no existing file needs migrating.
- Because it sits in `model/`, `rls._digest` and `_plans` pick it up for free.
- Its schema is `engine/schemas/v1/ontology.json`, plus one `LAYOUT` entry.

**What it points to, without copying anything:**

| Ontology field | Points to | Never copies |
|---|---|---|
| `objects[].table` | a keyed table in model.json; the key comes from model.json | the key, the columns, the types |
| `properties[].column` | a column of that table, or `table.column` of a table one-to-one with it (its key columns are a relationship onto the object's key, e.g. `ml_churn` or an input table) | the type (read from the lake) |
| `links[].via` | relationship IDs in model.json, in order | the join columns |
| `objects[].measures` | measure IDs | the MEL |
| `actions[].flow` | `flows/<id>.json` | the steps |
| `actions[].writes.table` | the object's table, or a table one-to-one with it (write-back by key) | anything |

**Derived, never stored:**
- **Cardinality**, walking `via`:
  - every hop with the relationship's many-to-one direction → many-to-one (one-to-one when the first hop's columns are the source table's key);
  - every hop against it → one-to-many;
  - mixed → many-to-many.
- **Property types**, from the lake.
- **The default property list**: every column of the table not hidden by a column rule. `properties` lists only the columns that need a name or a meaning.

**How `via` is walked.** Each relationship is walked along or against its many-to-one direction, whichever matches the table you are on. No hop may revisit a table.

**Brewline example**
- Tables: `cafes`, `customers`, `products`, `orders` and the generated `calendar`. The relationship IDs are what `model._rel` (95) makes: `orders-cafe_id`, `orders-customer_id`, `orders-product_id`.
- Two additions show a dimension ↔ dimension link and per-object recipients:
  - an input table `cafe_contacts(cafe_id key, manager, visit_reason)` with `add_relationship cafe_contacts.cafe_id → cafes.cafe_id`;
  - the scored ML model `churn`, whose table `ml_churn` is keyed by `customers_customer_id`.

**Derived for this example**
- `order_cafe` is many-to-one, so its inverse "orders" is one-to-many.
- `visited` and `bought` are many-to-many.
- A café's manager is a dimension ↔ dimension property, through the one-to-one `cafe_contacts`.

**The rule for picking a path** (one rule, used everywhere):
1. Following a named link uses its `via` exactly. Object reads never guess.
2. In `semantic_query`, a link named in the new `links: [ids]` decides how its target table is reached, for the whole query. Its `via` is added after the unique many-to-one path from the measure's fact to the link's source table.
3. Otherwise, a link marked `default: true` for that pair of tables.
4. Otherwise, today's rule: the unique shortest many-to-one chain (`planner.path`).
5. Otherwise the query is refused, and the message names the links that reach the table ("add `links: [visited]`").

Many-to-many links are used only when named or marked default. A query without `links` therefore plans exactly as today.

## 4. Migration

**Nothing is written on upgrade.**
- `model/ontology.json` doesn't exist in any 1.2.5 project, and nothing in the engine creates one by itself. `build_model` is unchanged (test #2).
- Every query, report, flow, agent and ML model plans the same SQL (golden test #1), because `links` is empty and no `follow` rule exists.
- The RLS views are byte-identical, and so are the cache keys.

**How an ontology arrives:**
1. In a project that is Ready (or after `abi_load`), the agent calls `propose_ontology`. This is read-only.
2. The agent refines names, plurals and descriptions using the vault (rule 9), and calls `save_ontology`.
3. ABI answers 409 with a preview: the diff, the lineage it touches, and any widening grants. The person clicks Confirm in the app (or chat); the model never sees the token.
4. The approval is one Git change, undoable. Owners approve `follow` links and Viewer-runnable actions; Editors approve the rest.
5. The app shows "Objects (proposed)" with an **Approve** button calling the same action, for people who don't use chat.

**If the person ignores it,** nothing breaks:
- every read stays on `semantic_query`, `visual_data` and datasets;
- object pages show "no object types yet";
- readiness does not require an ontology: it reports only dangling references, and only once one exists.

**When the ontology goes stale,** for example after a relationship change:
- `remove_relationship` refuses while a link uses it (#4);
- an import that breaks a reference is rejected whole (#3);
- so a stale ontology can't silently change a number.

**Exports and imports.** A 1.2.6 bundle carries `model/ontology.json`. A 1.2.5 engine refuses that path (open question 5).

## 5. Security review points

1. **Object lookup is a row-level door.** `get_object` and `list_objects` are the third row-level read, after the grid (`table_rows` 791) and step preview.
   - Same door: `semantic.execute` with `user_id`, RLS search path, `rls.check` (447), hidden columns left out (`rls.hidden`), query log, D-32 redaction for inbound.
   - Hidden and missing objects answer the same 404, with no count leak (as `get_position` 918).
   - Key values are cast literals built only by `_lit`, never interpolated raw.
   - `limit` is capped at 1000 (D-17).
2. **RLS through links.**
   - Traversal needs no new rule: every table in the semi-joins resolves to the person's views. Test #13.
   - `follow` computes keys by a system read but inlines only keys derived from the person's own visible rows. The views stay constant lists, never joins (GATE-4-fix-1).
   - It must not travel back along its own `via` (the anonymous-orders test).
   - It must be in `filtered`, `key_columns` and `explain`, or M3.6 shared partials would slice with the wrong columns. `test_rls_shared` with a follow link proves the outputs equal the person's own read.
   - `_unfiltered_outputs.roots` must follow the same edge, or ML tables on objects stay denied. Fail-closed is kept.
3. **Actions.**
   - Role, object visibility, inputs schema and checks run before any write. The write goes through `writeback._batch` as the runner, so it is logged and undoable.
   - Agent and inbound writes become proposals. Flows started by an agent need the person's yes.
   - Saving an action type that lets Viewers write or start a flow is an access widening: Owner plus confirmation (#16).
   - A flow started by an action runs as its owner (FL-6). Its `trigger.inputs` are a Viewer's typed text, so treat them as data: an agent step gets them through `_cap`, and they are never instructions.
   - In Viewer mode the harness still refuses `run_object_action` (index.ts 461). The person uses the app's button.
   - Production: allowed like `edit_cells` (D-57); definition changes stay dev-only.
4. **Recipients from data.**
   - Per-object sends go only to members who can see the object (#28).
   - The first send per domain is still confirmed (`_first_send` 505).
   - The attached data is the per-object query, grounded (`_grounded`).
   - Values a Viewer action writes into a recipient column can't redirect mail outside the members.
5. **Descriptions.** Agent-written ontology text can quote rows. For restricted Viewers it is masked in `ontology`, `semantic_model`, docs and the export, as `model.masked` (440) and `docs.mark` do.
6. **Export.**
   - JSON-LD and Turtle hold definitions only: no instances, no `${secret:…}`, no source hosts or URLs.
   - The IRI base defaults to `urn:abi:<project>:`.
   - There is no import path for RDF.
   - The bundle already excludes data and secret values (bundle.py; the app's Project zip text, app 1085).
7. **Ontology changes.**
   - `definition=True` gives Git authorship and undo.
   - Changes go through `imports.apply`, so schema, references, the Owner-only gates and the confirmation preview all run.
   - The cache digest is automatic (`rls._digest` covers `model/*.json`).
